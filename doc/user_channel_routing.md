# 用户专属渠道路由设计

> 状态：一期已实现。
>
> 目标：在用户使用同一个分组和模型时，根据“用户 + 使用分组”将请求限制在指定渠道集合中，再在这个集合内沿用现有的优先级、权重、重试、渠道亲和性和熔断能力。
>
> 一期范围：已实现独立配置项、用户/使用分组/模型规则匹配、指定渠道池过滤、`strict`/`default` 故障策略、渠道亲和性与异步任务入口校验、管理员日志，以及同页面双页签管理界面。规则筛选、修改时间和模拟路由属于后续增强。

## 1. 背景

当前渠道选择主要依据以下条件：

```text
使用分组
-> 模型和请求路径
-> 渠道可用状态及熔断状态
-> 渠道优先级
-> 渠道权重
```

用户 ID 不参与候选渠道筛选。因此，同一个分组中的不同用户请求同一个模型时，会进入相同的渠道候选集合。

核心场景如下：

```text
使用分组：sd2
该分组某个模型原本有渠道 1、2、3

用户 A 使用 sd2 -> 只允许渠道 1、2
用户 B 使用 sd2 -> 只允许渠道 3
未配置规则的用户 -> 仍按原逻辑使用渠道 1、2、3
```

渠道集合过滤完成后，不发明新的调度算法：

```text
用户 A -> 在渠道 1、2 中继续按原有优先级和权重选择
用户 B -> 只有渠道 3，直接选择渠道 3
```

实际运营中，同一分组内的用户可能有不同的上游质量和成本要求：

- 高质量用户只能使用稳定、质量较高的渠道。
- 普通用户使用标准渠道。
- 对质量要求较低的用户优先使用低成本渠道。

不建议为每个用户复制分组。分组应继续承担访问权限、可用模型和计费语义，用户渠道路由只负责缩小上游候选渠道范围。

## 2. 设计原则

1. **只缩小候选范围**：用户规则不能把不支持当前分组、模型或请求路径的渠道加入候选集合。
2. **不改变计费和权限**：规则不改变用户所属分组、可用分组、模型权限或价格。
3. **先限制渠道，再执行原调度**：先按用户规则过滤候选渠道，再在剩余渠道中计算原有优先级和权重；第一阶段不增加用户专属权重。
4. **所有入口一致**：首次选择、重试、跨分组重试、异步任务提交和渠道亲和性必须执行同一套规则。
5. **默认严格隔离**：指定渠道池不可用时默认失败，只有显式配置后才允许回退到分组默认渠道。
6. **可审计**：管理员能够确认请求命中了哪条规则、哪些渠道被过滤以及是否发生回退。
7. **请求路径无额外数据库查询**：规则加载后保存在内存中，按用户 ID 建立索引。

## 3. 术语

| 名称 | 含义 |
| --- | --- |
| 用户分组 | 用户账号自身所属的分组，用于权限和价格等现有业务语义 |
| 使用分组 | 当前请求实际选择渠道时使用的分组，即 `using_group` |
| 用户渠道集合 | 当前用户在指定使用分组下允许使用的一组渠道，第一阶段以渠道 ID 表示 |
| 严格失败 | 指定渠道池无可用渠道时返回 503，不进入该分组的其他渠道 |
| 默认回退 | 指定渠道池无可用渠道时，重新使用该分组的普通候选渠道 |

本文规则中的“分组”统一指请求的**使用分组**，不是用户账号自身所属分组。

## 4. 目标路由流程

```text
解析用户、使用分组、模型和请求路径
-> 获取原有的分组/模型候选渠道
-> 匹配用户渠道路由规则
-> 按规则中的渠道 ID 缩小候选集合
-> 排除停用、请求路径不匹配及熔断不可用的渠道
-> 在过滤后的集合中计算优先级
-> 在目标优先级内按权重选择渠道
-> 请求失败时仍在同一用户渠道策略内重试
```

关键约束：用户策略过滤必须发生在优先级集合计算之前。否则，如果该分组存在很多不属于用户渠道池的高优先级渠道，重试次数可能被这些无关优先级消耗，导致实际可用的低优先级渠道无法被选中。

## 5. 规则模型

第一阶段建议沿用现有设置项的 JSON 配置方式，不立即增加数据库表。

第一阶段以明确的渠道 ID 列表为主，直接表达“这个用户在这个使用分组下可以走哪些渠道”。建议的数据结构：

```json
{
  "rules": [
    {
      "id": "user-a-sd2",
      "name": "用户 A 的 sd2 渠道",
      "user_id": 106,
      "username": "user-a",
      "group_pattern": "sd2",
      "model_pattern": "*",
      "channel_ids": [1, 2],
      "fallback": "strict",
      "disabled": false
    },
    {
      "id": "user-b-sd2",
      "name": "用户 B 的 sd2 渠道",
      "user_id": 205,
      "username": "user-b",
      "group_pattern": "sd2",
      "model_pattern": "*",
      "channel_ids": [3],
      "fallback": "strict",
      "disabled": false
    }
  ]
}
```

### 5.1 字段说明

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | 稳定的规则标识，用于日志、编辑和排查，不使用数组下标代替 |
| `name` | 是 | 管理员可读的规则名称 |
| `user_id` | 是 | 用户 ID，必须大于 0 |
| `username` | 否 | 仅用于后台展示，不作为运行时匹配条件 |
| `group_pattern` | 是 | 使用分组名称，允许精确值或 `*` |
| `model_pattern` | 否 | 模型名称，允许精确值和 `*` 通配；空值等同于 `*` |
| `channel_ids` | 是 | 当前用户在该使用分组和模型范围内允许使用的渠道 ID |
| `fallback` | 是 | `strict` 或 `default`，默认 `strict` |
| `disabled` | 否 | 是否停用规则 |

`channel_ids` 不能为空且不能包含重复值。规则保存时可以检查渠道是否存在，但运行时仍必须重新检查渠道是否启用，以及是否支持当前使用分组、模型和请求路径。

### 5.2 为什么第一阶段使用渠道 ID

这个需求的核心是精确表达用户可以走哪些渠道。例如：

```text
用户 A + sd2 -> 渠道 1、2
用户 B + sd2 -> 渠道 3
```

因此，第一阶段直接保存渠道 ID 最清晰，也不会改变现有渠道标签的业务含义。

后台可以提供按标签批量勾选渠道的操作，但保存时仍展开成明确的渠道 ID 列表。这样管理员能准确看到规则当前包含哪些渠道。渠道被替换或删除后，后台应提示受影响的用户规则，后续也可以增加批量替换能力。

如果未来大量用户复用完全相同的渠道集合，再把渠道 ID 集合抽象成可复用的“渠道池模板”，用户规则绑定模板即可；第一阶段不需要先引入这层复杂度。

## 6. 规则匹配

只匹配 `user_id` 与当前用户完全相同且未停用的规则。

同一用户存在多条规则时，按以下顺序选择一条：

1. 精确分组 + 精确模型。
2. 精确分组 + 模型通配，模型模式中固定字符更多的优先。
3. 精确分组 + 全部模型。
4. 全部分组 + 精确模型。
5. 全部分组 + 模型通配，模型模式中固定字符更多的优先。
6. 全部分组 + 全部模型。

如果两条规则的匹配级别和模式具体程度完全相同，按配置中的先后顺序取第一条。保存时应拒绝相同用户、相同分组模式和相同模型模式的重复规则，后台也应提示可能发生覆盖的通配规则。

通配符第一阶段只支持 `*`，不支持正则表达式，匹配区分大小写并与现有模型名行为保持一致。

### 6.1 模型别名

如果用户模型视图将公开模型映射到了目标模型，渠道规则应匹配**映射后的目标模型**，因为渠道能力也是根据目标模型选择的。

管理员日志应同时记录原始请求模型和最终路由模型，避免排查时产生歧义。

### 6.2 `auto` 分组

当使用分组为 `auto` 时，不直接用字符串 `auto` 匹配规则。系统展开用户可用的自动分组后，针对每个实际分组分别匹配规则和筛选渠道。

例如自动分组依次尝试 `premium`、`default`：

```text
尝试 premium -> 匹配用户在 premium 下的规则 -> 在对应渠道池选择
失败后尝试 default -> 重新匹配用户在 default 下的规则 -> 在对应渠道池选择
```

`strict` 只禁止逃出当前实际分组命中的渠道池，不禁止现有的 `auto` 跨分组逻辑继续尝试下一个实际分组。若需要禁止跨分组，应继续使用现有跨分组重试配置，而不是给本功能增加第二套含义。

## 7. 无可用渠道时的行为

### 7.1 `strict`

指定渠道池中不存在满足分组、模型、请求路径、启用状态和熔断要求的渠道时：

- 不允许进入该分组中的其他渠道。
- 返回现有格式的 503“无可用渠道”错误。
- 对普通用户不暴露渠道 ID、渠道标签和熔断详情。
- 在管理员日志中记录严格策略失败原因和被排除的渠道摘要。

这是默认行为，可避免低成本渠道故障后自动使用高成本渠道，也可避免高质量用户被降级到低质量渠道。

### 7.2 `default`

指定渠道池全部不可用后：

1. 将本次请求标记为已回退，防止循环回退。
2. 重新使用该分组原有的全部候选渠道。
3. 继续应用原有的路径校验、熔断、优先级、权重和重试逻辑。
4. 在管理员日志中明确记录回退原因和最终渠道。

只有在指定渠道池所有优先级均不可用后才进行回退，不能因为当前最高优先级没有池内渠道就立即回退。

## 8. 与现有能力的关系

### 8.1 渠道优先级和权重

优先级和权重只在用户渠道池过滤后的集合中计算。

例如，分组中有以下渠道：

| 渠道 | 标签 | 优先级 | 权重 |
| --- | --- | ---: | ---: |
| A | premium | 10 | 100 |
| B | economy | 20 | 100 |
| C | economy | 10 | 50 |

如果用户 A 的规则只包含 A、C，那么只比较 A、C：先使用 A，重试进入下一优先级时再考虑 C；不在规则中的 B 即使全局优先级更高，也不会影响用户 A。

用户规则第一阶段不覆盖渠道自身的优先级和权重。同一个渠道在所有用户规则中仍使用渠道配置上的原始优先级和权重。本功能解决的是“哪些渠道有资格参与选择”，不是为每个用户再维护一套调度参数。

### 8.2 熔断

用户路由策略不绕过熔断：

- 渠道池中的熔断渠道仍应被排除。
- 半开探测仍受现有探测并发和探测归属逻辑限制。
- `strict` 规则在池内渠道全部熔断时失败。
- `default` 规则在池内渠道全部熔断时允许进入普通候选集合。

管理员排查信息需要区分“规则未包含此渠道”和“渠道被熔断排除”，不能统一显示为无可用渠道。

### 8.3 重试

每次重试必须携带相同的用户路由决策：

- `strict` 重试不能逃出指定渠道池。
- 重试可以进入池内的下一优先级。
- `default` 只有在池内候选耗尽后才能切换到普通集合。
- 已经失败的渠道和已有重试计数逻辑继续生效。

### 8.4 渠道亲和性

亲和渠道在复用前必须重新验证：

1. 渠道仍支持当前实际分组和目标模型。
2. 渠道仍支持当前请求路径。
3. 渠道满足当前用户命中的渠道路由规则。
4. 渠道未被现有熔断策略禁止。

如果亲和渠道不再属于用户渠道池，必须放弃本次亲和选择并执行正常路由。是否删除旧亲和记录继续遵循现有“渠道不可用时保留亲和”配置，但旧记录不能绕过当前用户规则。

成功请求记录新亲和关系时，只能记录本次策略实际允许的渠道。

### 8.5 异步任务

视频、图片及其他异步任务的**提交阶段**必须执行用户渠道规则。查询已有任务时应继续使用任务记录中的原渠道或上游任务信息，不能因用户规则后来变化而把查询请求发送到另一个渠道。

任务记录和管理员日志应保存提交时命中的规则 ID、渠道池和是否回退，保证后续能够解释任务为什么走到该渠道。

## 9. 后台管理设计

不新增独立的深层设置入口。配置继续放在现有页面：

```text
/system-settings/models/user-model-views
```

该页面内部拆成两个二级菜单（页签）：

```text
用户模型视图
用户渠道路由
```

- “用户模型视图”保留现有功能，并作为默认打开的菜单。
- “用户渠道路由”管理本文设计的“用户 + 使用分组 -> 渠道 ID 集合”规则。
- 两个菜单只共享页面入口，不混用配置数据，也不改变彼此的业务语义。
- 切换菜单不跳转到新的系统设置页面，避免继续增加入口层级。
- 当前默认打开“用户模型视图”；后续可通过查询参数（例如 `?tab=user-channel-routing`）保留刷新前的菜单。

页面结构建议：

```text
用户模型视图
├── 用户模型视图
└── 用户渠道路由
```

“用户渠道路由”的交互与现有用户模型视图保持一致，支持搜索用户、添加、编辑、停用和删除规则。

### 9.1 列表

列表至少展示：

- 规则名称和状态。
- 用户 ID、用户名和用户当前分组。
- 使用分组范围。
- 模型范围。
- 指定渠道 ID、渠道名称及其当前优先级和权重。
- 故障策略。
- 最近修改时间或配置顺序。

支持按用户、规则名称、分组、模型、渠道和状态筛选。

### 9.2 新增和编辑

建议按以下顺序配置：

```text
选择用户
-> 选择使用分组
-> 选择模型或填写模型通配符
-> 多选允许使用的具体渠道
-> 选择严格失败或默认回退
-> 查看规则预览
```

保存前校验：

- 用户存在。
- 分组模式不为空。
- 至少选择一个渠道 ID。
- 指定渠道 ID 存在。
- `fallback` 值合法。
- 规则 ID 唯一。
- 不存在相同作用域的重复规则。

如果当前没有任何渠道同时满足规则的分组、模型和渠道池，应允许管理员保存但给出明确警告，因为渠道可能稍后新增或启用。

### 9.3 模拟路由

提供管理员专用的“模拟路由”工具，输入：

```text
用户 + 使用分组 + 模型 + 请求路径
```

输出：

- 最终用于匹配的目标模型。
- 命中的规则及匹配级别。
- 原始候选渠道。
- 因用户规则被排除的渠道。
- 因停用、路径或熔断被排除的渠道。
- 各优先级剩余渠道。
- 预计是否触发默认回退。

模拟工具默认不发起真实上游请求，也不获取半开探测名额。

## 10. 日志和可观测性

管理员日志建议在 `other.admin_info` 下增加：

```json
{
  "user_channel_routing": {
    "rule_id": "user-a-sd2",
    "rule_name": "用户 A 的 sd2 渠道",
    "using_group": "sd2",
    "requested_model": "public-model",
    "routed_model": "target-model",
    "channel_ids": [1, 2],
    "fallback_mode": "strict",
    "fallback_used": false,
    "selected_channel_id": 2
  }
}
```

该信息只对管理员可见。普通用户日志不显示规则、渠道池、渠道 ID或熔断内部状态。

系统警告日志还应包含请求 ID、用户 ID、规则 ID、实际分组、模型和回退原因，便于与上游任务 ID及消费日志关联。

建议增加以下指标：

- 各规则的请求量和成功率。
- 各用户渠道集合的请求量和错误率。
- 严格策略无可用渠道次数。
- 默认回退次数及回退原因。
- 因亲和渠道不满足用户规则而重新选择的次数。

## 11. 后端集成点

后续实现预计涉及以下位置，实际开发时以当时代码为准：

| 位置 | 作用 |
| --- | --- |
| `setting/operation_setting/` | 保存、加载、规范化和索引用户渠道规则 |
| `service/channel_select.go` | 将用户规则与熔断条件组合，处理严格失败和默认回退 |
| `model/channel_cache.go` | 内存缓存模式下，在确定优先级前过滤候选渠道 |
| `model/ability.go` | 未启用内存缓存时执行完全相同的候选过滤语义 |
| `middleware/distributor.go` | 首次选择和亲和渠道复用前应用用户规则 |
| 任务提交及日志服务 | 保存规则命中、回退和最终渠道信息 |
| 管理员设置接口和前端 | 规则管理、校验和模拟路由 |

用户 ID、用户分组、使用分组、目标模型和请求路径已经可以从请求上下文或选择参数中获得。实现时应构造一个稳定的路由策略结果，并在首次选择、亲和和重试之间复用，避免同一次请求因配置读取时机不同而命中不同规则。

候选过滤器至少要组合以下条件：

```text
用户渠道规则允许
AND 渠道支持请求路径
AND 渠道启用
AND 熔断允许
```

内存缓存开启和关闭时必须返回一致结果。

## 12. 配置存储与扩展

### 第一阶段：Option JSON

适用条件：

- 规则主要用于少量特殊用户。
- 规则修改频率不高。
- 暂时不要求逐条修改历史审计。

实现要求：

- 配置解析时完成校验和规范化。
- 使用原子快照更新，不能让请求看到半份配置。
- 按 `user_id` 建立内存索引，不能每次扫描全部规则。
- 保存设置后立即刷新所有进程中的配置，遵循现有设置同步机制。

### 第二阶段：独立数据库表

出现以下情况时再迁移：

- 规则达到数百或数千条。
- 需要分页、批量分配和高频编辑。
- 需要操作人、修改时间和规则历史。
- 需要独立启停、审批或租户隔离。

数据库实现必须同时兼容 SQLite、MySQL 和 PostgreSQL，并使用 GORM 完成迁移和查询。

## 13. 错误处理

普通请求侧保持稳定、简洁的错误合同：

- 没有普通候选渠道：沿用现有“分组/模型无可用渠道”错误。
- 命中 `strict` 但渠道池不可用：同样返回 503，不泄露内部策略。
- 规则配置异常：保存时拒绝；运行时保留最后一份有效配置并记录系统错误。

管理员日志再给出精确原因，例如：

```text
no_channel_supports_group_model
assigned_pool_has_no_matching_channel
assigned_pool_channels_disabled
assigned_pool_channels_breaker_open
assigned_pool_probe_limit_reached
fallback_selected_default_pool
```

## 14. 测试计划

### 14.1 规则匹配

- 不同用户在同一分组、同一模型下命中不同渠道池。
- 精确模型优先于通配模型。
- 更具体的通配模式优先。
- 精确分组优先于全部分组。
- 停用规则不生效。
- 无规则用户保持原有路由行为。

### 14.2 候选选择

- 规则不能加入不支持当前分组或模型的渠道。
- 规则不能加入不支持当前请求路径的高级自定义渠道。
- 优先级只在池内渠道中计算。
- 权重只在同一池内、同一优先级中计算。
- 内存缓存开启和关闭时结果一致。

### 14.3 故障与重试

- `strict` 在池内渠道全部停用或熔断时返回 503。
- `strict` 的所有重试都不能逃出渠道池。
- `default` 仅在池内候选耗尽后回退。
- 回退只发生一次，不产生递归或重复重试。
- 半开探测名额不足时行为符合故障策略。
- `auto` 的每个实际分组独立匹配规则。

### 14.4 亲和性和任务

- 历史亲和渠道不属于当前用户池时不能复用。
- 亲和渠道仍属于用户池且可用时正常复用。
- 异步任务提交执行用户规则。
- 已有任务查询不因规则变化而切换上游渠道。
- 管理员日志记录规则、回退、最终渠道和上游任务 ID。
- 非管理员日志不暴露管理员路由信息。

## 15. 上线步骤

1. 实现“用户 + 使用分组 + 模型范围 -> 渠道 ID 集合”的规则解析和校验。
2. 建立按用户 ID 索引的内存快照和只读匹配接口。
3. 实现模拟路由，先验证规则效果，不影响真实请求。
4. 接入普通首次选择，并验证内存缓存开关两种模式。
5. 接入重试、熔断、亲和性和异步任务。
6. 增加管理员日志、指标和管理页面。
7. 先按“用户 A -> 渠道 1、2；用户 B -> 渠道 3”配置测试用户进行灰度。
8. 对比渠道命中、成功率、成本和熔断指标后扩大范围。

## 16. 验收标准

功能完成后，应满足：

- 同一分组、同一模型的两个用户可以稳定进入不同渠道池。
- 不配置规则的用户行为与上线前一致。
- 用户规则不会突破原有分组、模型和请求路径限制。
- 优先级、权重、重试和熔断在用户池内正常工作。
- 亲和性不能绕过用户规则。
- `strict` 和 `default` 的行为可通过自动化测试和管理员日志确认。
- 管理员能在不发起真实请求的情况下模拟规则结果。
- 内存缓存开启与关闭时行为一致。
- 普通用户看不到内部渠道策略和熔断详情。

## 17. 第一阶段不做的内容

- 不自动根据用户消费、错误率或信用等级动态调整渠道池。
- 不根据单个 API Token 配置不同渠道池。
- 不改变现有用户分组、模型权限或价格计算。
- 不提供正则表达式匹配。
- 不提供用户专属优先级或用户专属权重覆盖。
- 不提供可复用渠道池模板；第一阶段直接保存渠道 ID。
- 不因规则变更迁移或重定向已经提交的异步任务。
